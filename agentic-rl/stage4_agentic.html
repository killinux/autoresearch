奖励函数会真的取出 <calc> 里的表达式、在受限沙箱里执行，再拿结果判对错。 于是 GRPO 逼着模型学会"遇到不会算的就写算式调工具"，而不是瞎猜 —— 这就是工具调用 RL 的内核。

2奖励 = 真的跑工具（Reward System）

# Reward System 核心: 取 <calc> 里的表达式, 白名单校验后真的执行
def run_tool(text):
    expr = re.search(r"<calc>(.*?)</calc>", text).group(1)
    if not re.fullmatch(r"[\d\s+\-*/().]+", expr):   # 只允许算术, 防执行任意代码
        return None
    return eval(expr, {"__builtins__":{}}, {})       # ← 真的算

reward_tool_correct  # 工具结果 == 正确答案  -> +1.0
reward_used_tool     # 用了 <calc>...</calc>  -> +0.3

3训练效果：学会"写干净可执行的算式"

最妙的细节——GRPO 不只让它用工具，还把工具调用格式掰对了。

训练前
<calc>53 * 35 = 1855</calc>
带了 "= 1855"，工具无法执行(白名单拒绝) → 不得分
训练后
<calc>92 * 25</calc>
干净表达式 → 工具算出 2300 → 得分
正确率 75% → 100%。模型被"奖励=真执行工具"逼着学会了写 工具能真正跑起来的格式——这是死的指令教不会、只能靠 RL 试出来的。

4奖励设计的坑：可验证 = 天然防作弊

想靠"在 <calc> 里直接写答案数字"蒙混？它得先知道答案——可两位数乘法它不会， 所以唯一稳定拿分的办法就是写出真实算式 a*b 交给工具。 这正是计划阶段4 强调的「代码题不能靠 print 答案绕过单测」—— 可验证、难作弊的奖励，是 Agentic RL 的胜负手。

6⚠️ 诚实边界：这是"单轮"，真·多轮要 verl

单轮(本例)
生成一次 → 执行 → 打分
vs
多轮(真 Agentic)
看到工具返回 → 再思考 → 再调用 → …
TRL 的 GRPO 是单轮（生成一次就打分）。真正的多轮 Agentic（模型看到工具返回结果后 继续思考、再调用）需要自定义 rollout 循环 / 工业框架 verl（reward manager、sandbox、 multi-turn rollout）。本例抓住了最核心的「奖励 = 执行工具」这一点，多轮留作下一步上 verl。
